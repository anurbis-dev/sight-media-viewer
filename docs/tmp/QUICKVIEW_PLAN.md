# План: режим Quick View для Sight

Для агента. Сначала прочитай `CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/RECENT.md`. Соблюдай существующие конвенции (zero-build, `keys.js`, `json_body`, миграции в `Library._migrate()`). После каждого этапа: обнови `docs/RECENT.md`, при изменении стабильных фактов, то есть структуры, `docs/ARCHITECTURE.md`; подними `APP_VERSION`.

## Цель

Второй, минимальный режим запуска Sight: мгновенный просмотр файла с диска (аналог Quick Look), без индексации и без полного UI. Из превью можно одним действием открыть тот же файл в полном UI (библиотека, поиск, борды).

- Платформы: Windows, macOS, Linux. Первая цель: Windows (там достижима полная замена по скорости).
- Главный критерий: время от действия пользователя до видимого превью (см. бюджеты ниже).
- Преимущество перед конкурентами: богатый лайтбокс (3D, Gaussian splats, PSD, шрифты, PDF, единые зум/жесты) и переход в полный UI.

## Не цели (пока)

- Нативный плагин Quick Look для macOS (Swift).
- Глобальный хоткей «взять выделенное из файл-менеджера» (этап 5, опционально).
- Аннотации, синхронизация, мультипользовательность.
- Переписывание бэкенда на другой язык.

## Ограничения из текущей архитектуры

- Фронт без сборки; `index.html` содержит inline `<script type="module">`, из него нельзя импортировать. Вынесенные модули самодостаточны и получают зависимости через options (как `createCanvasView({...})`).
- Сервер слушает только `127.0.0.1`. Новые эндпоинты, читающие файлы по пути, нельзя оставлять открытыми (см. этап 2).
- Хоткеи только через `keys.js` (`hotkey`, `runHotkeys`, `KeyboardEvent.code`).
- CSS: для элементов с `[hidden]` используй `.foo:not([hidden]) { display:flex }`.
- Батч-эндпоинты принимают объект (`{"items": [...]}`), не массив.

## Бюджеты производительности (измерять, а не гадать)

| Сценарий | Цель |
|---|---|
| Хоткей/команда → окно с картинкой (процесс уже запущен) | ≤ 150 мс (Windows), ≤ 300 мс (mac/Linux) |
| Холодный старт превью (процесс не запущен) | ≤ 1,5 с |
| Следующий/предыдущий файл в папке (←/→) | ≤ 100 мс для изображений |
| Потребление RAM в трее в простое | зафиксировать; цель ≤ 150 МБ |

## Этап 0. Замеры и зачистка

1. Добавить в `Sight.py` и клиентский код простые метки времени (`performance.now()` на клиенте, лог на сервере) для: старта процесса, готовности сервера, показа окна, первой отрисовки картинки.
2. Записать базовые цифры в `docs/RECENT.md`.
3. Проверить, какие обработчики в `index.html` не должны работать в превью (индексация, сайдбар, тулбар), чтобы понять, что выносить.

Критерий готовности: есть таблица «сейчас» против бюджета.

## Этап 1. Вынести лайтбокс в модуль

1. Создать `app/static/lightbox.js` (ES-модуль, экспорт `createLightbox({...})`), перенести туда лайтбокс из `index.html`.
2. Всё внешнее передавать через options: источник контента, навигация (prev/next), настройки зума (`getZoomSettings`), `keysEnabled`, `markSmallSrc`, `syncPixelation`, колбэки закрытия и «открыть в библиотеке».
3. Убрать зависимость лайтбокса от id ассета из `library.db`: абстрактный «источник» с полями `{kind, url, name, path, mime, size}`. Библиотека и превью оба поставляют такие объекты.
4. Тяжёлые вьюеры (3D, splats, PDF, PSD, шрифты) подгружать лениво по типу файла (динамический `import()`), чтобы превью изображения не тянуло всё.
5. Регрессия: полный UI работает без изменений поведения (зум ПКМ/колесо, marquee не затронут, навигация, двойной клик).

Критерий готовности: полный UI использует `lightbox.js`, диффа в поведении нет.

## Этап 2. Режим «файл по пути» (бэкенд + страница превью)

1. Новая страница `app/static/preview.html`: минимальная разметка, импортирует `lightbox.js` и `keys.js`, никакого сайдбара/библиотеки.
2. Эндпоинты (замыкания в `build_app`):
   - `GET /api/preview/info?path=…` → метаданные, тип, список соседних файлов в папке (натуральная сортировка по имени), индекс текущего;
   - `GET /api/preview/file?path=…` → отдача файла (Range для видео/аудио);
   - `GET /api/preview/thumb?path=…&size=…` → миниатюра на лету (кэш в `SIGHT_HOME`, ключ по пути+mtime+size).
3. **Безопасность:** генерировать случайный токен при старте сервера, требовать его в каждом preview-запросе (заголовок или query). Токен передаётся только окну превью через аргументы запуска/IPC. Дополнительно проверять `Host`/`Origin` (защита от DNS rebinding). Никаких эндпоинтов записи для preview.
4. Навигация ←/→ по соседним файлам папки, Esc закрывает окно, пробел = закрыть/повторно открыть при желании.
5. Кнопка «Открыть в библиотеке»: `POST /api/preview/open-in-library` `{ "path": … }` → если папка не в источниках, предложить добавить как источник; открыть полный UI на этом ассете.

Критерий готовности: `Sight.py --preview <path>` открывает превью любого поддерживаемого типа; чужая страница в браузере не может прочитать файл.

## Этап 3. Резидентная оболочка (скорость)

Решение по движку принять по данным этапа 0, но по умолчанию:

**Вариант A (сначала, минимум переделок):** оставить Python-сервер и запуск окна через системный Chromium (`--app`), добавить иконку в трее (`pystray`; на GNOME нужен AppIndicator), режим «уже запущен»: повторный `Sight.py --preview <path>` шлёт запрос по локальному сокету/HTTP запущенному экземпляру и завершается.

**Вариант B (если A не укладывается в бюджет ≤150 мс):** Electron-оболочка. Тот же Chromium везде, предсозданное скрытое окно превью (показ 30–80 мс), нативный трей, глобальные хоткеи, ассоциации файлов. Python-бэкенд остаётся sidecar-процессом (порт и токен передаются оболочке). Фронт не переписывать.

Общее для обоих вариантов:
- Один экземпляр приложения (single-instance lock); второй запуск передаёт путь первому.
- Меню трея: «Открыть Sight», «Настройки», «Выход».
- Окно превью: без рамки/минимальный хром, всегда поверх по желанию, запоминает позицию и размер.
- Закрытие полного UI не завершает процесс (остаётся в трее); «Выход» завершает всё.

Критерий готовности: прогреть, нажать команду, окно с картинкой ≤ бюджета; измерить и записать.

## Этап 4. Интеграция с ОС (без хука на файл-менеджер)

1. Windows: ассоциация типов файлов «Открыть в Sight (превью)» и пункт контекстного меню Explorer; в установщике/`build_exe.bat` регистрация в реестре (HKCU), удаление при деинсталляции.
2. macOS: `Info.plist` с `CFBundleDocumentTypes` (Открыть с помощью), обработка `open-file` события; хоткей (опционально) через приложение.
3. Linux: `.desktop` файл с `MimeType=`, `Exec=… --preview %f`.
4. Аргумент командной строки `--preview <path>` работает одинаково на всех ОС.

Критерий готовности: на каждой ОС «Открыть с помощью Sight» показывает превью, повторное открытие не создаёт новых процессов.

## Этап 5 (опционально). Глобальный хоткей и выделение из файл-менеджера

- Windows: глобальный хоткей, активный только когда в фокусе Explorer; выделенный файл берётся через COM (`Shell.Application`).
- macOS: AppleScript/Accessibility для Finder (потребует разрешений, описать в MANUAL.md).
- Linux: только там, где реально работает (X11); на Wayland документировать ограничение.

## Этап 6. Документация и упаковка

1. `MANUAL.md`: раздел «Быстрый просмотр» (запуск, хоткеи, интеграция по ОС, ограничения).
2. Обновить `build_exe.bat` / `build_app_macos.sh` под новый режим и оболочку; проверить, что ffmpeg и превью-страница попадают в сборку.
3. `docs/ARCHITECTURE.md`: новые файлы, эндпоинты `/api/preview/*`, токен, схема single-instance.

## Порядок работы и приёмка

- Этапы идут строго по порядку, каждый оформлять отдельным коммитом (или серией) с записью в `docs/RECENT.md`.
- На каждом этапе прогонять ручную проверку: изображение, видео, аудио, PSD, PDF, шрифт, 3D модель, splat, файл с юникодным путём и пробелами, огромный файл.
- Если бюджет скорости не достигается, остановиться и описать результаты замеров перед выбором варианта B.
- Не расширять объём: всё из «Не цели» не трогать без отдельного решения.
