## 0.15.3 — 2026-11-10 — Launch: the window opens maximized and focused again
- **What:** If Sight was maximized when it was closed, it opens maximized again, and the window gets focus on launch. Before, neither happened on this machine. The window came up at its normal size, behind whatever had focus.
- **Where:** `Sight.py`: new `_process_tree(root)` (Toolhelp32 snapshot through ctypes); `_find_browser_window(pids, user32)` now takes a set of pids; `reveal_when_ready()` passes `_process_tree(proc.pid)`; `close_browser(proc)` terminates the same tree instead of running a PowerShell WMI query by `--user-data-dir` (0.15.2).
- **Notes:**
  - Root cause: the Popen'd `msedge.exe` is a launcher. It starts the real browser process and exits within a second with code 0. The window belongs to that child, so looking for a window owned by `proc.pid` never matched. `reveal_when_ready()` then returned after its 3 s search without calling `ShowWindow(SW_MAXIMIZE)` or `SetForegroundWindow`. The page's own `moveIntoView()` still brought the window on screen, which hid the bug.
  - The tree includes processes whose parent pid is the launcher's, even after the launcher has exited. `close_browser()` terminates the launcher first, so it cannot start the browser after the snapshot.
  - Checked by launching Sight.py on an isolated `SIGHT_HOME`. With a saved `max: true` the window was maximized and in the foreground (it was neither before the fix). With `max: false` it was not maximized and in the foreground. A start that fails, tested with a `library.db` that cannot be opened, leaves no Edge process behind.

## 0.15.2 — 2026-11-10 — Faster startup and asset list; folder dialog stays on top
- **What:** Sight starts faster and the library list loads faster. Measured on this machine with a copy of the real library (1,028 assets): a source launch (Sight.py) shows its window after 1.4 s instead of 3.9 s; server start to the first `/api/health` takes 1.1 s instead of 2.75 s; one `/api/assets` page of 400 takes 7.5 ms instead of ~20 ms. Sight.exe skips the dependency check, so it gains less, roughly 0.7–1 s of ~2 s by the estimate below (not measured, no exe was built). The Add-folder dialog can no longer open behind the Sight window.
- **Where:**
  - `Sight.py`: `has_deps()` checks the running interpreter in-process with `importlib.util.find_spec` (`DEP_MODULES`); `bootstrap()` re-execs straight into `~/.sight/runtime` when its `.deps-v4` marker exists; new `listen_socket()`; `main()` opens the socket and starts the browser before the server imports, then `server.run(sockets=[sock])`; `launched` dict + `launch_lock` + new `close_browser()` close a browser window opened for a start that failed; the plain-tab fallback waits for `server.started` (`_wait_serving`).
  - `library.py`: `USDZ_CONVERTER_VERSION` (moved from `usdz_convert.CONVERTER_VERSION`); ffmpeg search in a thread (`_search_ffmpeg`, `ffmpeg_exe()`); `_thumb_v` cache in `thumb_version(aid, fresh=False)` and `_forget_thumb()`.
  - `server.py`: `/api/assets` returns a `JSONResponse`; `/api/state` uses `lib.ffmpeg_exe()`; the folder dialog's PowerShell gives `ShowDialog` a hidden top-most owner form.
  - `fileinfo.py`: the one `NO_WINDOW` constant, imported by `library.py` and `server.py` (review of 0.15.1: the flag was spelled out in four places).
- **Notes:**
  - Where the time went (before): the `python -c "import fastapi, …, pymupdf"` dependency probe took 1.4 s per launch, and a Sight.bat launch ran it twice (once before and once after the re-exec into the venv). Importing `usdz_convert` only to read its version constant pulled in numpy (160 ms). `imageio_ffmpeg.get_ffmpeg_exe()` runs `ffmpeg -version` (160 ms). The launcher polled `/api/health` before the server listened, and on Windows a connect to a closed port takes ~2 s to be refused, so each attempt sat out its 0.4 s timeout. That cost ~0.5 s before the browser was even started.
  - Browser in parallel: Edge from launch to the page's ready ping takes ~330 ms warm (750 ms the first time a profile is created). It now overlaps the ~0.6 s of fastapi/uvicorn imports and library setup instead of following them. Its first request waits in the listen backlog until uvicorn takes the socket. On Windows the window stays off-screen until the page has content anyway. If the start fails, `main()` closes that browser through `close_browser()` so no window is left off-screen, and `launch_lock` keeps the launcher thread from starting one after that. Checked with a `library.db` that cannot be opened: no Edge process is left. (0.15.3 replaced the way `close_browser()` finds the browser.) A tab in the user's default browser (no Edge/Chrome found) still opens only once the server serves.
  - `listen_socket()` sets `SO_REUSEADDR` like `free_port()` and uvicorn's own bind, so the same port is picked as before (localStorage, including the cached theme colour, is per port).
  - `has_deps()` with `find_spec` finds a package without importing it, so a package that is present but broken now fails at the real import with a traceback instead of triggering a reinstall. `importlib.invalidate_caches()` runs first, so the check right after a pip install sees the new packages.
  - Thumbnail versions: every path that writes a thumbnail must call `thumb_version(aid, fresh=True)` (`_make_thumb`, `save_uploaded_thumb`, `psd_composite` do), and every path that deletes or invalidates one must call `_forget_thumb()` (all former `_have_thumb.discard` sites do). A missing file (version 0) is never cached.
  - Folder dialog: a console-less PowerShell started by the background server has no window and no foreground rights, so an ownerless `FolderBrowserDialog` can open behind the browser. Not reproduced, only reasoned. The owner form is a standard WinForms pattern and was checked to construct.
  - Still slow, not changed (numbers from `python -X importtime` and cProfile): importing fastapi + pydantic takes ~400 ms and uvicorn ~290 ms, most of what is left of server start. `build_app` (route and pydantic model setup) takes ~100 ms. Edge's own start takes ~250 ms. The client pulls every asset page back to back (400 per request), which is ~125 requests for a 50k library. `import("three")` + GLTFLoader take ~45 + 60 ms on the first 3D open per session.

## 0.14.1 — 2026-09-24 — Library: deleting a folder marks the files inside it missing
- **What:** Files inside a folder that is sent to the Recycle Bin, or moved out of a watched source, now turn "missing" right away. Before, they stayed "ready" until the next rescan or restart. It looked like a text-file bug only because the reported case was a folder holding only `.log`/`.ini` files (Unreal crash folders).
- **Where:** `library.py`: new `Library._mark_gone(fp)`, used by the watchdog handler's `on_deleted` and by the `on_moved` fallback (files only).
- **Notes:**
  - On Windows, watchdog reports a folder recycle or a move out of the tree as ONE `deleted` event for the folder, with `is_directory=False` (the path can no longer be stat'ed). So every deleted path is treated as a possible folder: `_mark_gone` matches the path itself plus `substr(path,1,len(prefix)) = prefix + os.sep`. It uses `substr`, not `LIKE`, so `%`/`_` in names don't need escaping. `shutil.rmtree`-style deletes already sent one event per file. Renaming a folder inside the tree sends per-file `moved` events and already worked.
  - `excluded` rows are not flipped to missing, same as `scan_source`. The path match is case-sensitive, same as everywhere else.
  - Missing entries are still never removed automatically. Only a manual purge removes them (the 🧹 button on the sidebar's Missing row, the grid context menu, or the palette → `/api/missing/purge`). Scans only set the status, and `_reconcile_moved` carries metadata over to moved files.

## 0.12.1 — 2026-09-24 — 3D: explode guards for models with huge part counts
- **What:** Explode can no longer freeze the page on a model split into thousands of tiny meshes (e.g. one mesh per face). Up to 1000 parts per assembly it uses the explosion graph. Bigger assemblies, and any assembly reached after a 400 ms budget, use a simple axial mode: each part moves along the dominant axis of its offset from the assembly center. Above 50,000 meshes in total the explode control is hidden.
- **Where:** `index.html`: `EXPLODE_GRAPH_MAX` / `EXPLODE_MAX_MESHES` / `EXPLODE_BUDGET_MS`, `buildExplodeRig` (`solveAxial`, one post-order pass for "has a mesh", BFS queue instead of recursion, `place` / `pushAll` / `largest` helpers), `applyExplode` (iterative over `rig.list`, reusing a per-item `off` vector).
- **Notes:**
  - Measured: 800 touching parts (graph) 134 ms, 3150 (axial) 21 ms, 60,000 rejected in 4 ms.
  - Nothing may spread a per-part array into arguments (`Math.max(...x)`, `push(...x)` throw a RangeError at ~100k elements) or recurse per part (ride-along chains can be thousands long). `rig.list` is the removal order reversed, which puts every carry before the parts that ride on it.
  - The budget is checked between assemblies, so one graph solve (≤1000 parts, ~250 ms worst case) can overrun it once.

## 0.12.0 — 2026-09-24 — 3D: assembly-aware explode (explosion graph, grounded part, one axis per part)
- **What:** Explode no longer pushes every top-level child radially away from the center. It follows the explosion-graph method of Li, Agrawala, Curless & Salesin (SIGGRAPH 2008), which is also how CAD auto-explode behaves: the largest part of each assembly stays put, every other part slides out along one model axis (±X/±Y/±Z) in an unblocked direction, parts ride along with the part they rest on, and sub-assemblies from the file's node hierarchy move as a unit and then explode inside themselves. The slider is staged: top-level parts first, then their insides, each part easing in turn.
- **Where:** `index.html`: `buildExplodeRig(THREE, obj)` (replaces the radial `explodeMap` build in boot3d), `applyExplode(rig, t)` (signature changed, `explodeScale` removed).
- **Notes:**
  - Solved once per load, with `obj` temporarily at identity so the model's own axes are the canonical directions; offsets are stored in each part's parent-local space, so the 90° turns never invalidate them. "Up" (the preferred direction on ties, down is least preferred) is the model axis that maps to world up at load time.
  - Assembly = a node with 2+ children that contain meshes (single-child wrappers are skipped). A Mesh is always atomic. Flat files (OBJ, most STL-to-glTF) get one level.
  - Blocking and contact use precise **bounding boxes**, not geometry (the paper uses real geometry and splits containers — not done). A part nested inside another's box is blocked on all sides; the fallback then removes the part with the fewest blockers. Expect odd but valid results for concentric parts and large voxel-like grids of equal parts (long ride-along chains).
  - Cost is O(n²·6) for the pair tests; escape distances are cached and invalidated for the neighbours of each removed part. 800 touching parts solve in ~140 ms.
  - Explode still moves parts by `position` only; `fitRig` sets t = 0 to measure the floor.

- **What:** a model whose meshes share one material now shows 1 material (was one per mesh). The info overlay's Materials / Textures / Meshes are collapsible (click the header, closed by default, remembered), each list scrolls on its own; a new Meshes list (name, triangles, materials) highlights a mesh on click. `U` or the new *UV* toolbar button splits the 3D lightbox: UV pane | divider | model. The UV pane shows the selection's UVs (orange; all UVs in white with nothing selected) over its base-color texture and pans/zooms like an image; `F` and 1–9 go to the pane under the cursor. While the split is on, the *i* button and the info panel move to the model's side.
- **Where:** `index.html`: `cloneModel` (one clone per material), `attachPanScroll` (nested), new `bindSplitDrag` (the library/board divider now uses it too), `lightPane` in the `pointerover` hover router, `attachViewer(…, opts)` (`embedded`, returns `{fit, zoom}`), `#v3dShade [data-act=uv]`, keydown (KeyF / digits / KeyU in the 3D block), `renderLightInfo` / `inspectSection` / `onLightInfoClick`, `toggleUV` / `syncUvPane` / `refreshUv`, `makeModelInspector` (`matEntry` merge, `meshes`, `targets`, `renderUV`), CSS `.light-info .sec`, `.li-list`, `.uv-pane`, `.light-frame.uv-on`, `--uv-left`.
- **Notes:**
  - Cause of the wrong count: `cloneModel` (every open of a cached model, and the first open too) cloned the material per mesh, turning one shared material into N instances (also N shader programs). Fixed at the source; the inspector additionally merges instances with the same `type|name` (FBX/OBJ loaders can create per-mesh copies).
  - UV picture: rendered by the viewer's renderer into a W×H render target (texture size, 2048–4096 on the long side), geometry drawn with `gl_Position = uv` (ShaderMaterial; three declares `uv` for it), fill + wireframe, multi-material meshes limited to the selected groups; read back, sRGB-encoded, `toBlob` → object URL (revoked on replace/close). glTF: v = 0 at the image top (texture `flipY` false); with a texture its `flipY` decides. Only the first UV set is drawn. A 4096² render stalls the main thread for a moment (readback + pixel loop); it is redrawn on every selection change while the split is on.
  - UV mode (`sight.uvMode`) and the split ratio (`sight.uvSplit`) persist; the pane is removed on every asset switch (`showInLight` → `syncUvPane`) and re-added by `boot3d` once the inspector exists, so images/splats never get it. Info section state: `sight.infoOpen` `{mat, tex, mesh}`.
  - Tested with Playwright on an isolated `SIGHT_HOME`: 30 meshes / 1 material GLB (now "1 material · 30 meshes"), 1-mesh / 3-texture GLB, UV toggle, divider drag, 2 → 200% and F → Frame on the UV pane under the cursor, no console errors.
